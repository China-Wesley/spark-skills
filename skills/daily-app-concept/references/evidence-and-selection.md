# 需求证据与选题

## 证据门槛

正式选题至少具备：

1. 两条普通用户的直接反馈，来自应用商店评论、垂直社区发帖或讨论回复。开发者自己的推广文案不能充当这两条反馈。
2. 一个已上线可比产品的市场证明。优先使用可独立查看的评分与评论量；开发者或公司公开披露的下载、活跃、收入或付费数据必须标记为未经第三方审计。
3. 一个官方平台或技术来源，用于确认关键能力、系统限制或实现边界。
4. 一个从现有反馈中收窄的产品切口。只证明大类需求存在不够，必须说明本方案避开了哪些竞品已有功能和复杂度。

优先近 90 天证据；长期稳定痛点可以补充较旧材料。记录发布日期、访问日期、来源身份、可见热度与样本范围。搜索摘要只能用来发现线索，结论要回到原页面核对。

## 来源强弱

- 强：应用商店当前评分与评论量、评论正文、公开可核验产品页、多个普通用户独立表达同一问题。
- 中：开发者或公司公开数据、Product Hunt 发布、社区高互动帖。使用时标注自述或样本局限。
- 弱：官网营销文案、单个推广帖、没有用户回复的产品介绍、二手汇总。只用于发现方向。

不要把评分量等同收入，不要把下载等同留存，不要把评论愿望等同付费承诺。

## 新增行为成本

每个候选单独回答：

- 用户在什么时刻触发？
- 每次要多做几步？
- 多久发生一次？
- 是否立刻得到回报？
- 忘记操作或识别失败会造成什么后果？
- 产品能否承接用户已经发生的行为或系统可读取的数据？

核心价值依赖长期额外拍照、分类、填写或维护，而当下没有明确收益时，原则上淘汰。

## 个人开发适配评分

每项 1–10 分，并附一句依据：

| 维度 | 判断问题 |
| --- | --- |
| 需求强度 | 用户是否反复遇到，现有替代是否明显痛苦？ |
| 用户清晰度 | 能否用一句话说清谁在什么时刻需要它？ |
| MVP 一人可行性 | 核心链路能否在数周内完成，无需重后台和运营？ |
| 差异化 | 是否找到比大类更窄、更明确的任务？ |
| 获客入口 | 能否在垂直社区、搜索或相关场景找到首批用户？ |
| 付费可能性 | 是否有相邻付费产品，或能明确节省时间、金钱和错误成本？ |

需求证据缺失或一人可行性明显不足时直接换题。差异化偏弱但需求和可行性强时，只能得出“适合小规模验证”，并写清竞争风险。
