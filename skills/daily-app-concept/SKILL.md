# Daily App Concept

交付一个有真实需求证据、与历史实质不同、产品闭环清楚且视觉能解释核心行为的移动 App 概念。研究清单、候选标题、绘图提示词、未经目视复核的图片或 `draft` manifest 都不是完整交付。

## 成功定义

完整交付必须同时满足：

- 至少三个实质不同的候选经过证据、历史和一人开发可行性筛选。
- 选中方向能用“谁，在什么时刻，通过什么动作，立即得到什么结果”说明。
- 核心一屏、操作前状态和操作后状态形成可信闭环。
- 5–7 张独立 PNG 已实际生成并完成联系表与 100% 目视复核。
- `manifest.json` 使用当前 schema，状态为 `complete`，最终校验返回 `ok: true`。

## 入口路由与能力预检

先判断请求属于哪条路径：

| 请求 | 处理 |
| --- | --- |
| 寻找需求、验证机会、定义 App 并制作概念图 | 执行完整流程，默认路径 |
| 用户明确只要需求研究或产品定义 | 执行相应阶段，交付标记为部分结果，不生成图片、不声称 `complete` |
| 已有明确产品，只需要 UI 原型或传播视觉 | 转入专门设计流程，不重新做需求发现 |
| 要求编码、测试、上架或发布 | 不使用本 Skill，进入对应生命周期阶段 |

完整流程开工前确认联网调研、工作区写入、图像生成和图像查看能力。缺少联网能力时只能基于用户提供材料形成证据受限的草案；缺少图像生成或查看能力时停在产品定义或视觉方案，不能伪造图片、评分或完成状态。

将当前 Skill 的目录记为 `<skill-root>`。以下脚本命令均从该目录运行；若运行环境 cwd 不在 Skill 目录，使用脚本绝对路径，不能假设用户工作区里存在 `scripts/`。

## 工作流

### 1. 建立真实历史

确定日期、输出目录和目标设备。默认输出到用户指定工作区的 `outputs/daily-app-concept/YYYY-MM-DD/`。

调研前搜索用户指定根目录、当前工作区和相邻历史目录中的 `manifest.json`、`index.json`、`选题台账.json`、旧 `concept.md` 与废案记录。读取已完成、被否决、废弃和重做版本；被否决需求仍占用题目，被否决视觉模板仍进入禁用样式。查看最近 7 组图片并记录产品五元组和视觉指纹。

若确实是首次运行，必须先确认上述位置均无历史，并检查当前对话中的既有想法；把原因记录为 `first_run_reason`。空目录本身不是新颖性证据。

详细规则见 [需求证据、选题与查重](references/evidence-and-selection.md)。

### 2. 研究并查重三个候选

每个候选分别评估用户痛点、替代行为、行为成本、竞品覆盖、一人可行性和历史碰撞。候选之间只换名称、配色、人群形容词或功能包装不算不同。

正式方向至少具备两条普通用户直接反馈、一个已上线可比产品的市场证明、一个官方技术来源，以及从大类需求中收窄的切口。分别标记直接证据、市场证明、开发者自述和模型推断。

把三个候选写入 `working/candidates.json` 后运行：

```bash
python3 scripts/check_novelty.py --candidate <candidate.json> --history <history-file-or-root> --json
```

只有在已完成历史搜索且确认没有任何记录时，才允许显式运行：

```bash
python3 scripts/check_novelty.py --candidate <candidate.json> --allow-empty-history --json
```

脚本会逐个比较所有候选。它只是文字相似度安全网；最终仍需判断是否是同一用户在同一时刻做相同动作并得到相同结果。`warn` 必须写明人工判断理由；`reject` 候选不得入选。

### 3. Gate A：证据、重复与窄产品

提交方向前检查：证据门槛已达到、候选不是历史重复、行为成本合理且一个人能验证。用一句话写清：

`谁，在什么时刻，通过什么核心动作，立即得到什么结果。`

再定义 App 名、目标用户、触发、核心任务、核心一屏、3–5 步流程、竞品边界、MVP、明确不做、技术可行性、收费假设和主要风险。优先无需账号、内容冷启动、长期人工运营或昂贵 API 的本地优先产品。

把全部候选及其 `selected` / `rejected` 决策写入 manifest，确保未来查重能同时排除已选方向和废案。Gate 未通过时返回候选与缺口，不进入视觉制作。

### 4. 研究并选择视觉方向

先研究真实产品流程，再研究 3–6 个作者或官方设计案例。只提炼层级、信息密度、状态反馈、排版、色彩、组件或动效逻辑；记录原始链接、作者、访问日期、采用的方法和许可判断。

正式出图前提出三套结构不同的方向，分别写清主构图、页面节奏、产品隐喻、与最近 7 期的差异，以及为什么不是“居中手机 + 大标题 + 卡片 + 换色”。

这是昂贵且主观的 Gate：普通交互任务先把三套方向展示给用户选择；用户明确要求端到端自动完成或运行于无人值守流程时，按“核心行为可读 → 产品特异 → 信息层级 → 系列延展 → 视觉新鲜度”自动选择。无论哪种模式，都在 manifest 记录 `selection_mode` 和可回读的 `selection_evidence`。

详细规则见 [视觉研究与质量门槛](references/visual-system.md)。

### 5. 先做核心 UI，再扩展图组

先画核心一屏、主操作前状态和操作后状态，确认信息结构、唯一主操作和变化结果成立，再做封面与说明页。每个视觉元素必须承担识别、信息、状态或操作作用。

默认制作 5–7 张独立 PNG，至少覆盖 `problem`、`solution`、`core-screen`、`state-change` 和 `outcome`。至少 3 张清楚显示产品 UI；前两张合起来必须讲清问题、动作和结果。产品未开发时标注“App concept”或“概念设计，尚未上线”。

### 6. Gate B：目视复核与修订

生成后必须实际查看图片并完成两轮检查：

- 联系表：检查整组节奏、重复构图、叙事顺序，以及产品机制是否连续出现。
- 100%：检查字体、间距、图标、裁切、中文、数据、状态、控件和核心界面可信度。

再按产品特异性、信息层级、核心 UI 可信度、序列变化、可读性和完成度各打 1–10 分。任一项低于 8、存在 blocking issue 或仍像通用模板，就修正最弱页面并重新查看；不能用文案解释替代界面修改。无法实际查看图片时不得通过 Gate。

### 7. 保存、校验并写回历史

输出结构和 manifest schema 见 [交付与校验](references/deliverables.md)。至少包含 `research.md`、`concept.md`、`visual-system.md`、`manifest.json` 和 `images/`。

先以 `draft` 状态检查结构：

```bash
python3 scripts/validate_output.py <output-dir> --allow-draft --json
```

修复全部错误并完成目视复核后，将状态改为 `complete`，再运行最终校验：

```bash
python3 scripts/validate_output.py <output-dir> --json
```

只有最终结果返回 `ok: true` 才能声称完成。manifest 本身就是后续历史的一部分；全部候选、视觉指纹和用户否决原因必须保留。完成只表示研究、定义和图片齐全，不代表产品已开发、发布或获得市场验证。

## 失败恢复与停手线

| 触发条件 | 首选处理 | 仍失败时 |
| --- | --- | --- |
| 没有历史文件 | 扩大搜索并检查对话先验 | 记录首次运行原因，显式使用 `--allow-empty-history` |
| 候选被判 `warn` | 人工比较五元组并记录理由 | 有争议就淘汰 |
| 候选被判 `reject` | 更换核心触发、动作或结果 | 三个候选都重复则返回重新调研 |
| 证据不足或来源不可读 | 寻找一手替代来源 | 降级为草案，不进入完整交付 |
| 图像生成失败 | 保留产品与视觉规格，重试一次等价通道 | 停在视觉方案，不伪造文件 |
| 无法查看图片 | 请求可用的查看能力 | 保持 `draft`，不填写通过评分 |
| 校验失败 | 按错误逐项修复并复跑 | 报告未完成项，不静默跳过 |

不要替用户执行编码、上架、发布、付费、购买素材或其他超出概念交付的副作用。

## 最终交付

直接给出选中需求、证据强弱、与最近历史的差异、App 定义、MVP、收费假设、竞争风险、视觉方向和实际文件链接。报告图片数量、尺寸、唯一哈希、最低视觉评分和最终校验结果；部分流程必须明确停在哪一阶段以及缺少什么，不能包装成完整交付。
