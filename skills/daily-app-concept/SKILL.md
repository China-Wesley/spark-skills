# Daily App Concept

完成一个经证据筛选、跨历史查重、产品逻辑清楚且视觉能解释核心行为的移动 App 概念。研究清单、候选标题、绘图提示词或未经目视复核的图片都不是完成状态。

## 适用范围

用于寻找 App 机会、把模糊问题收窄成可验证 MVP，或在开发前把核心体验做成可读视觉概念。如果产品范围已经确定且用户要原型、代码、测试或上架，直接进入对应阶段。

## 开始前：建立真实历史

确定日期、输出目录和设备。默认输出到用户指定工作区的 `outputs/daily-app-concept/YYYY-MM-DD/`。

开始调研前必须建立排除历史，不能只读当前输出目录的新索引：

1. 搜索用户指定根目录及相邻历史目录中的 `manifest.json`、`index.json`、`选题台账.json` 和旧概念说明。
2. 读取全部历史条目，包含已完成、被用户否决、废弃和重做版本。被否决的需求仍然占用题目，被否决的视觉模板仍然进入禁用样式。
3. 查看最近 7 组图片，记录需求、目标用户、触发、核心对象、核心动作、结果，以及版式、主角结构、配色、字体和设备呈现。
4. 检查当前对话中已提出或被否决的想法。没有历史文件时，把对话先验写入临时排除表；空索引绝不等于题目新颖。

详细查重规则见 [需求证据与选题](references/evidence-and-selection.md)。可先运行：

```bash
python3 scripts/check_novelty.py --candidate <candidate.json> --history <history-file-or-root> --json
```

脚本是文字相似度安全网，不能替代对“同一用户是否仍在同一时刻做同一动作得到同一结果”的语义判断。

## 工作流

### 1. 研究三个真正不同的候选

每个候选都评估用户痛点、替代行为、行为成本、竞品覆盖、一人可行性和历史碰撞。候选之间只换名称、配色、目标人群形容词或功能包装不算不同。

正式方向至少具备两条普通用户直接反馈、一个已上线可比产品的市场证明、一个官方技术来源，以及从大类需求中收窄的切口。分别标记需求证据、市场证明、开发者自述和仍是推断。门槛与评分方法见 [需求证据与选题](references/evidence-and-selection.md)。

### 2. 先否决重复，再定义窄产品

用一句话写清：

`谁，在什么时刻，通过什么核心动作，立即得到什么结果。`

逐项与全部历史比较目标用户、触发、核心对象、核心动作和结果。五项中核心动作相同且触发或结果近似时直接淘汰；换平台入口、增加 Widget、换视觉风格或缩小一点范围都不能洗掉重复。

选中后定义 App 名、目标用户、触发、核心任务、核心一屏、3–5 步流程、竞品边界、MVP、明确不做、技术可行性、收费假设和主要风险。优先无需账号、内容冷启动、长期人工运营或昂贵 API 的本地优先产品。

### 3. 锁定视觉方向，而不是套模板

先研究真实产品流程，再研究 3–6 个作者或官方设计案例。只提炼层级、信息密度、状态反馈、排版、色彩、组件或动效逻辑；记录原始链接、作者、访问日期、采用的方法和许可判断。

在正式出图前提出至少三套结构不同的视觉方向。每套都要写清：

- 主构图和页面节奏。
- 产品对象或行为如何成为视觉隐喻。
- 与最近 7 期的版式、主角结构、配色、字体和设备呈现有何不同。
- 为什么不是“居中手机 + 大标题 + 卡片 + 换色”的通用海报模板。

选定一套后写入视觉指纹。相邻概念至少更换产品场景和主视觉结构，并在版式、主配色、表达角度中再更换两项。详见 [视觉研究与质量门槛](references/visual-system.md)。

### 4. 先做可信核心屏，再扩展图组

先画核心一屏与关键状态，确认信息结构、主操作和变化结果成立，再做封面和说明页。每个视觉元素必须承担识别、信息、状态或操作作用；无法说明作用的装饰删除。

默认制作 5–7 张独立 PNG，至少覆盖：

1. `problem`：具体问题。
2. `solution`：核心动作与即时结果。
3. `core-screen`：可信核心一屏。
4. `state-change`：操作前后可见变化。
5. `outcome`：真实闭环。

至少 3 张清楚显示产品 UI。前两张必须让陌生人看懂问题、动作和结果。产品未开发时标注“App concept”或“概念设计，尚未上线”。

### 5. 强制视觉复核

生成后必须用图像查看能力完成两轮检查：

- 联系表检查：整组节奏、重复构图、叙事顺序、产品机制是否在至少三张图中连续出现。
- 100% 检查：字体、间距、图标、裁切、中文、数据、状态、控件和核心界面是否可信。

再按产品特异性、信息层级、核心 UI 可信度、序列变化、可读性和完成度各打 1–10 分。任一项低于 8，或仍像通用模板，就重做最弱页面；不能用文案解释替代界面修正。无法实际查看图片时不得标记完成。

### 6. 保存、校验和记入历史

输出结构见 [交付与校验](references/deliverables.md)。至少包含 `research.md`、`concept.md`、`visual-system.md`、`manifest.json` 和 `images/`。

```bash
python3 scripts/validate_output.py <输出目录> --json
```

校验通过后才能把状态写为 `complete`。把成功概念、被否决候选、最近相似项、视觉指纹和用户否决原因写回历史。完成只表示研究、定义和图片齐全，不代表产品已开发、发布或获得市场验证。

## 最终交付

直接给出选中需求、证据强弱、与最近历史的差异、App 定义、MVP、收费假设、竞争风险、视觉方向和实际文件链接。说明图片数量、尺寸、唯一哈希、最低视觉评分与校验结果。
