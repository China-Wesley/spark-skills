# 产品契约与交互建模

## 从一句想法收窄成可验证任务

原型要回答体验是否成立，不负责证明市场需求。先把输入整理成以下契约：

| 字段 | 要回答的问题 |
| --- | --- |
| 目标用户 | 谁会在真实生活或工作中使用？ |
| 触发时刻 | 什么情况让他现在就打开产品？ |
| 当前阻力 | 他目前为什么慢、错、烦或不确定？ |
| 核心对象 | 用户真正操作的业务对象是什么？ |
| 核心动作 | 用户最想完成的一个动作是什么？ |
| 即时结果 | 动作完成后，什么变化证明产品有用？ |
| 本次不做 | 哪些能力不会影响这条任务的判断？ |

产品契约不是功能列表。若一句话里出现“以及、同时、顺便”，先判断这些内容是否影响同一个结果；否则从第一版中删掉。

## 把任务画在时间轴上

页面是空间，体验是时间。先用表格写主任务：

| 步骤 | 用户看到 | 用户动作 | 系统反馈 | 下一步为何清楚 |
| --- | --- | --- | --- | --- |
| 1 | 触发相关的起始状态 | 选择主操作 | 控件即时响应 | 唯一主要动作继续突出 |
| 2 | 完成动作所需信息 | 输入或选择 | 校验、预览或计算 | 结果和代价可预期 |
| 3 | 确认前状态 | 提交 | 加载并防止重复提交 | 成功或失败去向明确 |
| 4 | 完成结果 | 查看、撤销或继续 | 结果写入界面 | 用户知道任务已完成 |

每增加一个页面都要说明它消除了什么不确定性。能在当前页面用展开、弹层或局部状态解决时，不要为了数量新增页面。

## 状态矩阵

只制作影响任务判断的状态：

- `default`：用户刚进入时看到什么，主动作是否清楚。
- `input`：填写、选择或拖动后界面如何变化。
- `loading`：系统正在处理什么，能否取消或避免重复操作。
- `empty`：没有数据时用户如何开始，不用假统计填满。
- `success`：结果发生了什么变化，下一步是什么。
- `error`：错误原因、保留的信息、修复动作和重试入口。
- `undo`：高代价动作是否能撤销，撤销后状态如何恢复。

不是每个产品都要展示全部状态。支付、删除、上传、识别、生成、同步等不确定或高代价操作，至少覆盖加载、失败和恢复。

## 原型交互契约

在 `prototype-spec.json` 中用稳定选择器描述真实操作。推荐格式：

```json
{
  "schema_version": 1,
  "status": "complete",
  "title": "产品名",
  "mode": "mobile",
  "screens": [
    {"id": "home", "name": "首页", "purpose": "发起核心任务"},
    {"id": "compose", "name": "编辑", "purpose": "完成必要输入"},
    {"id": "result", "name": "结果", "purpose": "确认即时价值"}
  ],
  "primary_journey": {
    "id": "create-item",
    "name": "创建一条记录",
    "start_screen": "home",
    "steps": [
      {
        "action": "click",
        "selector": "[data-test=\"start\"]",
        "expect": {"screen": "compose", "visible": "[data-screen=\"compose\"]"}
      },
      {
        "action": "fill",
        "selector": "[data-test=\"title-input\"]",
        "value": "周五前完成初稿"
      },
      {
        "action": "click",
        "selector": "[data-test=\"save\"]",
        "expect": {"screen": "result", "text": {"selector": "[data-test=\"result-title\"]", "includes": "周五"}}
      }
    ]
  }
}
```

支持的浏览器动作是 `click`、`fill`、`select`、`press` 和 `wait`。一个步骤可以检查 `screen`、`visible` 和 `text`。选择器优先用 `data-test`，避免依赖易变的样式类名或按钮文案。

## 常见误判

- 有五张好看的页面，不等于有一条能走通的任务。
- 页面能跳转，不等于操作改变了状态。
- 弹出“成功”提示，不等于用户看到了真实结果。
- 复刻竞品布局，不等于理解了该产品的交互逻辑。
- 原型覆盖所有功能，不等于验证了最重要的问题。
