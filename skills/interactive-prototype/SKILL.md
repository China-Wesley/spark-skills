# Interactive Prototype

把一个产品想法变成能真实操作的体验证据。完整交付不是几张界面截图，也不是一套前端组件，而是一个能在电脑浏览器中打开、沿主任务走通并让用户判断“这个产品用起来是否成立”的高保真原型。

## 成功定义

完整交付必须同时满足：

- 产品意图、目标用户、使用时刻和核心结果已经写清，关键假设可回读。
- 至少一条主任务从起点、关键操作到结果反馈可以真实点击走通。
- 核心页面包含与任务有关的默认、空、加载、成功、失败或撤销状态；不只切换静态画板。
- 视觉层级、内容密度、控件和反馈符合目标平台，且使用产品自己的对象与文案。
- `index.html` 可在电脑浏览器中展示原型：移动端位于可缩放的手机窗口中，桌面端位于浏览器窗口中。
- 静态校验通过；具备 Playwright 时，主任务自动点击通过且没有页面脚本错误。

## 入口路由与能力预检

先判断任务范围：

| 请求 | 处理 |
| --- | --- |
| 已有产品想法，需要 UI、交互动线或可点击原型 | 执行完整流程 |
| 只有一句模糊想法，但目标用户和结果可以合理推断 | 记录假设后直接做第一版，用可见原型帮助校准 |
| 还在寻找值得做的需求 | 转入需求发现 Skill，不把猜测包装成产品定义 |
| 只要海报、封面、概念图或纯静态界面 | 使用对应视觉流程，不声称完成交互原型 |
| 要求生产代码、后端、真实登录、支付或上架 | 原型只用于定义体验；实现交给开发阶段 |

完整流程开始前确认工作区可写、能打开本地 HTML，并检查用户是否提供了设计系统、现有产品、截图、品牌资产、竞品参考或代码仓库。已有上下文优先复用；没有时从产品行为推导视觉，不套通用 AI 模板。

将本 Skill 目录记为 `<skill-root>`。脚本从该目录调用，不要假设用户工作区里已经存在 `scripts/` 或 `assets/`。

## 工作流

### 1. 写清产品契约，不先堆页面

创建 `prototype-brief.md`，用简短事实回答：谁、在什么时刻、想完成什么、当前阻力是什么、最小成功结果是什么、哪些能力明确不在本次原型中。区分用户提供的事实、从现有材料得到的事实和为了推进第一版而做的假设。

抽取产品中的核心对象和状态。例如记账产品的对象不是“卡片”，而是账单、账户、分类和统计区间；这些对象决定界面语言。详细方法见 [产品契约与交互建模](references/product-and-interaction.md)。

### 2. 先画时间上的任务，再画空间上的页面

只选择一条最需要验证的主任务，写成：

`触发 → 起点 → 用户动作 → 系统反馈 → 下一决定 → 完成结果`

再由任务推导屏幕、弹层和局部状态。每一步都写明用户看到什么、做什么、系统如何反馈、下一步为什么清楚。补上真正会改变判断的分支；不要为了显得完整设计大量无关页面。

把屏幕和可执行步骤写进 `prototype-spec.json`。主任务通常应包含 2–6 个有效操作，并至少覆盖一次明确反馈。

### 3. 选择平台与交付形态

- 用户明确 App、iOS、Android、手机或随身场景时选择 `mobile`。
- 用户明确后台、工作台、数据密集操作、键鼠效率或大屏时选择 `desktop`。
- 同一产品必须同时验证手机和电脑时选择 `responsive`，分别定义信息优先级，不能只把桌面页面等比缩小。
- 信息不足且产品明显面向普通消费者时，默认 `mobile`。

独立原型默认使用原生 HTML、CSS 和 JavaScript，避免构建与 CDN 依赖，保证文件可直接打开。若用户已有代码库或明确技术栈，则在现有栈中实现，并保留同样的浏览器预览和验收契约。

### 4. 建立视觉方向

从品牌资产、现有界面和真实产品参考中提炼层级、密度、排版、色彩和动效逻辑。没有现成方向时，在内部比较三种结构差异明显的方案，并按“任务清晰度 → 产品特异性 → 平台适配 → 可实现性 → 视觉辨识度”选择一版。只有用户明确要挑方向时才暂停展示多版。

不要把紫色渐变、悬浮玻璃、圆角卡片、无意义图标或大面积空白当作高保真。高保真来自真实对象、可信内容、完整状态和精确反馈。平台与视觉规则见 [视觉与平台适配](references/visual-and-platform.md)。

### 5. 初始化浏览器交付物

运行：

```bash
python3 <skill-root>/scripts/init_prototype.py \
  --output <output-dir> \
  --title "<product-title>" \
  --mode mobile
```

脚本创建 `index.html` 浏览器展示壳、`prototype.html` 交互画布、`prototype-brief.md`、`prototype-spec.json` 和 `prototype-report.md`。生成物处于 `draft`，只是可运行骨架；必须替换产品内容、移除 scaffold 标记并完成规格后才能交付。

移动端在电脑中默认显示为居中的手机窗口，支持重置、设备尺寸切换、单独打开应用和演示模式；桌面端显示为浏览器窗口。不要删掉这些浏览器验收能力去换一组静态截图。

### 6. 实现真实交互

先完成主任务，再补视觉细节。按钮、输入、选择、开关、返回、弹层、导航和错误恢复必须修改真实状态；禁止用热点图、不可见链接或“点击任意位置跳下一页”冒充交互。

每个关键动作使用稳定的 `id` 或 `data-test` 选择器，并与 `prototype-spec.json` 中的步骤一一对应。为用户提供即时反馈；耗时动作有加载状态，破坏性动作可确认或撤销，失败后能恢复。键盘焦点、可读标签、对比度、点击区域和减少动态效果也属于高保真。

### 7. 验证并修订

先运行静态校验：

```bash
python3 <skill-root>/scripts/validate_prototype.py <output-dir> --json
```

校验会拒绝 `draft`、未替换骨架、缺失屏幕或选择器、重复 ID、外部脚本依赖和不可读控件。若仍在制作，可临时加 `--allow-draft` 查看结构问题，但这不支持完成结论。

若本地具备 Playwright，再运行真实浏览器主路径：

```bash
node <skill-root>/scripts/browser_smoke.mjs <output-dir>
```

打开生成的 `screenshots/overview.png` 和逐步截图，至少检查一次完整任务、一个恢复路径、手机窗口与桌面浏览器布局、窄屏可读性以及控制台错误。脚本缺少 Playwright 时改用当前浏览器逐步点击并记录人工证据，不能把静态校验说成真实交互通过。

完整规格、命令和故障恢复见 [浏览器交付与验收](references/browser-delivery-and-qa.md)。

## 失败恢复与停手线

| 情况 | 处理 |
| --- | --- |
| 需求太模糊 | 只补会改变主任务的假设，其余先做可见第一版 |
| 没有品牌或参考 | 从核心对象和使用场景生成独立视觉语言，不复制竞品独特表达 |
| 没有图片或图标 | 使用有许可的真实素材、本地资源或克制的文字占位，不生成伪品牌资产 |
| 浏览器自动化不可用 | 完成静态校验并人工点击；明确记录未自动验证 |
| 外部资源导致离线失败 | 下载允许使用的素材并改为相对路径，或移除非必要资源 |
| 主路径走不通 | 优先修流程、状态和反馈，再处理装饰细节 |

不要在原型中接入真实账号、支付、生产数据库或不可逆外部操作。不要把可点击原型描述为已实现、已发布或已经市场验证的产品。

## 最终交付

给出原型路径、浏览器打开方式、平台模式、已走通的主任务、包含的关键状态、静态校验结果、浏览器验收结果和仍属于假设的内容。链接到 `index.html`、`prototype-brief.md`、`prototype-spec.json` 和 `prototype-report.md`；截图用于佐证，不能替代可操作原型。
